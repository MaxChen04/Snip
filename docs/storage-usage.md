# Storage meter

Opening the account menu reads `/api/storage`. After checking the session, Snip
reuses a calculated storage summary for up to five minutes. Captures and deletions
can take that long to appear in the meter. Reopening the menu does not extend the
summary's lifetime.

The summary uses the native [Workers Cache API](https://developers.cloudflare.com/workers/runtime-apis/cache/),
with a separate cache namespace and a key scoped to the request origin and the
installation's session secret. Each installation should keep its own
`SESSION_SECRET`, as generated by setup. No new binding, paid storage service, or
scheduled job is needed. The actual API response remains `private, no-store`;
every request still passes session authentication before the internal cache is
read.

The cache is best effort and local to a Cloudflare data center. On a cold,
expired, or evicted entry, the request waits for the existing R2 listing scan:
up to 40 pages of 1,000 objects. Different data centers and simultaneous cold
requests can each run a scan. This reduces repeat reads; it does not guarantee
one scan globally every five minutes. A cache failure falls back to scanning,
and a failed scan is not cached. Local development and desktop use the same
runtime cache when available, and still work without it.

The existing `partial` flag is preserved when a scan reaches the listing bound.
The meter is an informational estimate of stored objects, not a quota or an
account billing total. It does not prevent uploads, cap storage, or delete files.
